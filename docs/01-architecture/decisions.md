| 2026-11-06 | 進行制御はStep Functions | Lambdaの15分上限に影響されず、ターンごとに再試行できる | Lambda単体で全ターンを実行 | 確定 |
| 2026-11-06 | 発言保存と配信をDynamoDB Streamsで切り離す | 配信方式を後から変えてもエンジンに影響しない | エンジンから直接配信 | 確定 |
| 2026-11-06 | モデル混在はBedrockのConverse APIで扱う | 役割とモデルの対応を設定だけで変えられる | モデルごとの個別API | 確定 |
| 2026-11-06 | 認証を最初から組み込む(Cognito、サインアップ無効) | 後から追加すると改修範囲が大きい | 公開時に追加 | 確定 |
| 2026-11-06 | 「購読 → 履歴取得」の順で処理する | 「履歴取得 → 購読」だと、その間に生成された発言を取りこぼす(当初案の誤りを訂正) | 履歴取得 → 購読 | 確定 |

| 2026-11-07 | Step Functionsの発言生成の呼び出し方(Lambda経由 / 直接統合)を比較検討 | - | - | 下の行で決定 |
| 2026-11-09 | 発言生成はStep FunctionsからLambdaを呼び、LambdaがBedrockを呼ぶ | 設定・履歴の読み込み、話者と段階の決定、プロンプトの組み立て、条件付き保存といった独自の処理が必要 | BedrockのSDK直接統合(往復は減るが、履歴の組み立てなどをステートマシン内で表現する必要がある) | 確定 |
| 2026-11-09 | リソース名の接頭辞は `agorawl`。スタック名は `AgorawlData` などとし、テーブル名などはCDKの自動生成に任せてスタックの出力で参照する | 同じアカウント内で本システムのリソースを見分けられる。名前を固定しないと、作り直しや複数環境で衝突しない | テーブル名を固定する | 確定 |
| 2026-11-09 | 開発初期はテーブルの削除ポリシーをDESTROYにし、本番運用の前にRETAINへ戻す | 動作確認の後に `cdk destroy` で跡を残さず片付けられる | 初期設定のまま(RETAIN。削除してもテーブルが残る) | 確定 |
| 2026-11-09 | Step Functionsのワークフロー種別はStandard | Expressは1回の実行が最大5分で、19ターンの議論は超えるおそれがある。コンソールで各ターンの経過を追える。費用の差はこの規模では無視できる | Express | 確定 |
| 2026-11-12 | スタックは Data・Engine → Auth・Api → Realtime → Web の順に作る。画面のない段階は、動作確認用CLIで確かめる(Issue #38) | 議論エンジンが議論として成立したので、画面を作って一連の流れを完成させる。下の層から作れば、段階ごとに本物のAWSの上で確かめられる | 画面から作る(APIや配信がないと動かせない) | 確定 |
| 2026-11-12 | Debatesにも Streams(NEW_IMAGE、MODIFYのみ)を付け、議論の状態の変化(終了、判定の保存)を配信する。配信Lambdaは、MessagesとDebatesの2つの Streams から起動する。失敗時は、再試行2回、失敗したバッチを半分に分けて再試行し、それでも失敗した分はSQSに送って後続を止めない(Issue #41) | 判定の結果と完了はDebatesに保存されるため、Messagesだけでは終了を知らせられない。判定には十数秒かかり、画面に取り直しを繰り返させるより、変わったときに知らせるほうがよい。配信の失敗で後続の発言が止まらないようにする | 最後の発言を受け取ったら、画面がHTTP APIで取り直しを繰り返す(判定を待つ間の呼び出しが増える)。エンジンが完了時に配信Lambdaを直接呼ぶ(エンジンは保存するだけ、という方針に反する) | 確定 |
| 2026-11-12 | SPAの配信を、入れ物(HostingStack。S3 + CloudFront。依存なし)と中身(WebStack。ビルドしたSPAと `config.json`。すべてに依存)の2つのスタックに分ける。AuthStackとApiStackは、HostingStackのCloudFrontのドメインを、コールバックのURLとCORSに使う(Issue #45) | CognitoとHTTP APIはCloudFrontのドメインを、SPAはAPIのURLを必要とし、1つのスタックでは依存が輪になる。入れ物を先に作れば、依存が一方向になる | 1つのWebStackのまま、Cognitoのコールバックのあとから書き換える仕組みを入れる(設定がスタックの外で変わり、分かりにくい)。独自のドメインを先に決める(ドメインの取得と証明書が要る) | 確定 |
| 2026-11-12 | 費用の通知を AWS Budgets で作る。CDK の BudgetStack に予算を1つ置き、月の実績の費用が 50・100・150・200・250 ドルを超えたらメールで知らせる。アドレスは手元の設定ファイル `infra/local.json`(コミットしない)に書く。数える範囲はアカウント全体(Issue #54) | 不正なアクセスなどで議論を大量に動かされても、今は請求まで気づけない。CDK にすれば設定がリポジトリに残り、作り直しても消えない。50ドルごとに知らせれば、増え方が分かる。1つの予算に付けられる通知は5つまでなので、250ドルまでとする | コンソールで手で作る(設定が残らない)。予算の 50%・80%・100% と月末の見込みで知らせる(Issue の当初の案)。予算を増やして 250ドルより上も50ドルごとに知らせる。アドレスを毎回のデプロイで CDK の context か環境変数で渡す(毎回の手間がかかり、渡し忘れると予算のスタックがデプロイされない)。タグで絞る(Bedrock の呼び出しの費用にタグが付かず、肝心の費用を数えられないおそれがある)。サービスで絞る(Claude の費用が請求でどのサービス名になるか確かめていない。Agorawl 以外の費用の急増にも気づけない) | 確定 |
| 2026-11-13 | 管理者への通知用に、SNSのトピックを置く NotifyStack を足す。送り先は、費用の通知と同じ管理者のメールアドレスとし、`infra/local.json` の名前を `budgetEmail` から `adminEmail` に変える(Issue #55) | 議論の開始の通知をメールで送るため。トピックを1つにしておけば、ほかの通知(ログインのロックなど)にも使える。費用の通知と議論の通知の送り先は同じ管理者なので、設定を1つにまとめる | Lambdaから SES でメールを送る(送信元のアドレスの検証が要る)。トピックを ApiStack に置く(ほかのスタックから使いにくい) | 確定 |
