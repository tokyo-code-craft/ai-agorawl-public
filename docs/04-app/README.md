# 04-app: 起動・表示

## 構成要素

| 要素 | 役割 |
|---|---|
| HTTP API | 操作を受け付ける。議論の作成(テーマと2つの立場の投入)、一覧、履歴取得。Cognito JWTで認可(→「HTTP API」) |
| WebSocket API | 新しい発言をサーバーから即時に届ける。接続・購読・切断を管理 |
| 配信Lambda | Streamsのトリガーで起動し、購読中の接続へ送信 |
| SPA | 議論の経過をリアルタイムに表示する(S3 + CloudFront)。React + Vite + TypeScript で作り、`contract/` の型をそのまま使う |

- HTTP APIはサーバーからブラウザへ自発的に送れないため、配信にはWebSocketを使う。生成そのものにはどちらのAPIも関与しない。
- 議論の一覧は、作成者に関係なく全件を新しい順に返す(DebatesのGSI `byCreatedAt` → `02-data-model`)。

## 時系列(新規の議論)

| 順 | API | 起点 | 挙動 |
|---|---|---|---|
| 1 | WebSocket | ブラウザ | 接続。接続IDが発行されConnectionsに保存される |
| 2 | HTTP | ブラウザ | テーマと2つの立場の投入。議論IDが即座に返る |
| 3 | WebSocket | ブラウザ | 議論IDを購読する。接続IDに議論IDが紐付く |
| 4 | HTTP | ブラウザ | 履歴を取得する(直後は空) |
| 5 | なし | サーバー | Step Functionsが1ターンずつ生成し、Messagesに保存 |
| 6 | WebSocket | サーバー | 保存を検知した配信Lambdaが、購読中の接続へ送信 |
| 7 | WebSocket | サーバー | ターンごとに5〜6を繰り返し、終了時に完了通知を送る |
| 8 | WebSocket | ブラウザ | 切断で接続情報が削除される。再接続時は接続→購読→履歴取得をやり直す |

- 既存の議論を開く場合は、接続 → 購読 → 履歴取得の順。
- 購読より前に生成された発言は履歴取得で補い、重複は `turn` で排除する。
- 発言には、討論者の作戦メモ(`notes`)が含まれる(→ `02-data-model`)。作戦メモは、議論の終了後に開示する。議論中は表示しない(→ `03-engine`「作戦メモ」)。

## HTTP API

| メソッドとパス | 内容 |
|---|---|
| `POST /debates` | 議論を作成し、エンジンを起動する。議論IDを返す |
| `GET /debates` | 議論の一覧(新しい順。一般のユーザーには、隠した議論を除く) |
| `GET /debates/{debateId}` | 議論1件と、その全発言 |
| `PATCH /debates/{debateId}` | 議論を一般のユーザーに見せるか隠すかを切り替える。管理者だけ(→「議論を隠す」) |
| `DELETE /debates/{debateId}` | 議論1件と、その全発言を消す。管理者だけ(→「議論を消す」) |
| `GET /models` | 議論の作成で選べる討論者と審判のモデルの一覧と、既定のモデル |
| `GET /accounts` | アカウントの一覧。管理者だけ(→「アカウントの一覧」) |

- すべての呼び出しに、Cognitoのアクセストークンを `Authorization: Bearer <トークン>` で付ける。API GatewayのJWTオーソライザーで検証し、トークンがない・誤っている場合は401を返す。
- 本文はJSON(UTF-8)。
- 時刻はISO 8601(UTC、ミリ秒まで)の文字列。

### `POST /debates`

リクエスト:

```json
{ "theme": "虎と熊は戦ったらどちらが強いか", "positions": { "pro": "虎派", "con": "熊派" }, "maxTurns": 10, "models": { "pro": "jp.anthropic.claude-sonnet-4-6", "con": "jp.anthropic.claude-haiku-4-5-20251001-v1:0", "judge": "global.anthropic.claude-opus-4-6-v1" } }
```

| 項目 | 内容 |
|---|---|
| `theme`、`positions` | 必須。検証のルールは `02-data-model`「設定の検証ルール」 |
| `maxTurns` | 省略可。省略時は10。HTTP APIで作れるのは10ターンまで(4〜10の偶数)。`02-data-model` の検証ルール(4〜50)に加えて確かめ、超えたら400を返す。11ターン以上の議論は、開発用CLI(`tools/start-debate`)でだけ作れる |
| `models` | 省略可。先攻(`pro`)と後攻(`con`)の討論者のモデルID。それぞれ省略でき、省略した側は既定のモデルを使う。選べるモデル(下の「選べるモデル」)にないモデルIDは400を返す。先攻と後攻で違うモデルでも、同じモデルでもよい。指定したモデルで `participants` を作る。審判(`judge`)のモデルIDも指定できる。省略すると既定の審判を使う。指定すると、既定の審判(`judges`)の全員のモデルをそれに替える(人数と観点はそのまま)。審判で選べるモデル(下の「選べるモデル」)にないモデルIDは400を返す |
| 選べないもの | 審判の人数と観点は、APIの既定値(`judges`)を使う。既定値と既定のモデルは、`03-engine`「動作確認用のモデルの組み合わせ」と同じ組み合わせとし、ApiStackがLambdaの環境変数で渡す(コードに固定しない) |

処理:

1. 本文を読み、`models` が選べるモデルにあるかを確かめ、既定値と合わせて `validateDebateSettings`(`contract/`)で検証する。違反があれば400を返し、何も保存しない。
2. 実行中の議論があれば、409を返し、何も保存しない(下の「同時に実行できる議論」)。
3. テーマと立場が議論として適切かを、AIに確かめさせる。適切でなければ400を返し、確かめられなければ503を返す。どちらも何も保存しない(下の「入力の内容の確認」)。
4. デモのアカウントなら、今日作った数を1つ足す。上限を超えるなら429を返し、何も保存しない(下の「デモのアカウントが1日に作れる議論」)。
5. 議論IDを発行し(UUID v4)、Debatesに保存する。`ownerId` はトークンのユーザーID(`sub`)、`status` は `running`、`createdAt` は現在時刻、`listKey` は `"ALL"`。`theme` と立場の名前は、前後の空白を除いて保存する。
6. エンジン(Step Functions)を、起動入力 `{ "debateId": "…" }` で起動する(→ `02-data-model`「起動入力」)。起動に失敗したら、Debatesの `status` を `failed` にして500を返す。
7. 管理者にメールで知らせる(下の「議論の開始の通知」)。
8. 201で `{ "debateId": "…" }` を返す。

#### 同時に実行できる議論

議論を大量に動かされて費用が膨らむのを防ぐため、同時に実行できる議論を、全体で1件に限る。

| 項目 | 内容 | 状態 |
|---|---|---|
| 上限 | 全体で1件。作成者に関係なく数える。管理者も例外にしない | 確定 |
| 実行中の数え方 | エンジンのステートマシンの実行のうち、実行中(`RUNNING`)のものを数える(`ListExecutions`)。判定の間も実行中に含まれる | 確定 |
| 上限に達したとき | 409で `{ "message": "実行中の議論があります。終わってから作ってください" }` を返す。画面は、この文言をそのまま出す | 確定 |
| 同じ瞬間の作成 | 2つの作成がほぼ同時に届くと、どちらも実行中の議論を見つけられず、2件とも始まることがある。この規模では起こりにくいため、防がない | 確定 |

#### 入力の内容の確認

デモのアカウントはだれでも使えるため、議論にならない入力や、有害な入力で議論を作らせない。文字の形(長さ、使えない文字)は `02-data-model`「設定の検証ルール」で先に確かめ、ここでは中身を確かめる。

| 項目 | 内容 | 状態 |
|---|---|---|
| 対象 | すべてのアカウント(管理者も含む) | 確定 |
| 確かめる順 | 本文の検証(400)と実行中の議論(409)の後、デモの数を足す前。断られた作成は、デモの1日の数に入れない | 確定 |
| 確かめ方 | Bedrock の Converse API で、AI にテーマと先攻・後攻の立場を見せ、欄ごとに適切か(`theme_ok`、`pro_ok`、`con_ok`)と、断るときの理由(`reason`。記録用で、画面には出さない)を、ツールの入力の形で返させる。入力は確かめる対象のデータとして渡し、中に書かれた指示には従わせない | 確定 |
| モデル | Claude Haiku 4.5(`jp.anthropic.claude-haiku-4-5-20251001-v1:0`)。コードに固定せず、ApiStack が Lambda の環境変数 `CONTENT_CHECK_MODEL_ID` で渡す | 確定 |
| 断るもの | (1) 議論にならない(問いや論点になっていない。意味のない文字列、単なる語、雑談など)。(2) 立場がテーマに合わない(2つの立場が、テーマへの対立する答えになっていない)。(3) 有害(実在の個人や団体をおとしめる、差別、性的な内容、犯罪や危険な行為のやり方、自傷)。(4) AI への指示を含む(議論の進め方や AI の振る舞いを変えようとする文)。(5) 政治(政党、政治家、選挙、法律や政策の賛否など、政治的な主張を争う)。(6) 宗教(宗教・宗派・信仰の是非や優劣を争う) | 確定 |
| 欄ごとの判断 | テーマは (1)・(3)〜(6) で、先攻と後攻の立場はそれぞれ (2)〜(6) で見る。テーマが不適切なときは、テーマだけを不適切とする(立場は、テーマを直した後の作成であらためて確かめる) | 確定 |
| 通すもの | 上のどれにも当たらないもの。軽いテーマやふざけたテーマ(食べ物、趣味、架空の対決、生活の選び方、技術の比べ方など)も通す | 確定 |
| 断ったとき | 400で `{ "message": "このテーマと立場では議論を作れません", "errors": [...] }` を返す。`errors` には、不適切な欄ごとに「テーマが不適切です」「先攻の立場が不適切です」「後攻の立場が不適切です」を入れる。どの基準に当たったかの細かい理由は出さない。画面は、ほかの検証の違反と同じく `errors` を出す。断った入力と理由は、ログに残す | 確定 |
| 確かめられないとき | AI の呼び出しに失敗した、時間内に答えが返らない、答えの形が違う、のどれかなら、作らずに503で `{ "message": "入力を確かめられませんでした。少し待ってから、もう一度作ってください" }` を返す | 確定 |
| 待つ時間 | AI の答えは15秒まで待つ。HTTP API の Lambda の時間の上限は29秒(API Gateway の上限30秒の手前) | 確定 |

#### デモのアカウントが1日に作れる議論

デモのアカウント(→「アカウントの種類」)は、動画の視聴者が使う。費用が膨らみすぎないよう、1日に作れる議論の数を限る。

| 項目 | 内容 | 状態 |
|---|---|---|
| 上限 | デモのアカウント1つにつき、1日5件。同じデモのアカウントを使う人は、全員で5件 | 確定 |
| 対象 | デモのアカウントだけ。管理者と一般のアカウントには上限がない | 確定 |
| 1日の区切り | 日本時間の0時 | 確定 |
| 数え方 | ApiStackのDynamoDBのテーブル DailyCreates(PK: `counterKey`。`<sub>#<日本時間の日付 YYYY-MM-DD>`)の `created`(数値)を、作るたびに1つ足す。足す前の値が上限に達していれば足さずに断る(条件付きの更新)。行は、2日後に消す(TTL の `expiresAt`) | 確定 |
| 数える順 | 本文の検証(400)、実行中の議論(409)、入力の内容の確認(400・503)の後に数える。断られた作成は数えない。数えた後でエンジンを起動できなかった議論も、1件と数える | 確定 |
| 消した議論 | 数えたまま減らさない(作って消してを繰り返せないようにする) | 確定 |
| 上限に達したとき | 429で `{ "message": "今日作れる議論の数(5件)に達しました。明日また作ってください" }` を返す。画面は、この文言をそのまま出す | 確定 |

#### 議論の開始の通知

HTTP APIで議論を始めるたびに、管理者にメールで知らせる。身に覚えのない議論に気づけるようにする。

| 項目 | 内容 | 状態 |
|---|---|---|
| 送り方 | SNSのトピック(管理者への通知用。NotifyStack → `01-architecture`)に発行する。トピックがメールで管理者に送る | 確定 |
| 送り先 | 管理者のメールアドレス(`infra/local.json` の `adminEmail` → `01-architecture`「費用の通知」と同じ) | 確定 |
| 件名 | `[Agorawl] 議論が始まりました: <テーマ>`(SNSの件名の上限100文字に収まるよう、長いテーマは切り詰める) | 確定 |
| 本文 | テーマ、先攻と後攻の立場、ターン数、作成者(`ownerId`)、作成の時刻、議論の画面のURL(`<SPAのオリジン>/debates/<議論ID>`) | 確定 |
| 送れなかったとき | 議論はそのまま続け、201を返す。送れなかったことはログに残す | 確定 |
| 対象 | HTTP APIで作った議論だけ。開発用CLI(`tools/start-debate`)で作った議論は知らせない | 確定 |

#### 選べるモデル

| 項目 | 内容 | 状態 |
|---|---|---|
| 一覧 | 下の表のとおり。ApiStackがLambdaの環境変数で渡す(コードに固定しない)。画面は `GET /models` で受け取る | 確定 |
| 既定のモデル | 先攻・後攻とも Claude Haiku 4.5(`03-engine`「動作確認用のモデルの組み合わせ」と同じ) | 確定 |
| 入れる条件 | 立ち絵があるグループのモデル(→ `05-persona-illustration`)で、東京リージョンから、エンジンと同じ呼び方(Converse、temperature 0.7、検索の道具を渡して結果を返す往復)で呼べることを確かめたもの。今は Claude、OpenAI、Mistral。ほかのグループは、立ち絵を用意したら足す | 確定 |

|---|---|---|
| Claude Haiku 4.5 | `jp.anthropic.claude-haiku-4-5-20251001-v1:0` | 速くて安い。いつもの討論者 |
| Claude Sonnet 4.6 | `jp.anthropic.claude-sonnet-4-6` | 賢さと速さのバランス型 |
| Claude Opus 4.6 | `global.anthropic.claude-opus-4-6-v1` | いちばん賢いが、遅くて高い |

| Mistral Large 3 | `mistral.mistral-large-3-675b-instruct` | Mistral の大きいモデル。長めに話し、相手の主張に一つずつ答える |

審判で選べるモデル:

| 項目 | 内容 | 状態 |
|---|---|---|
| 一覧 | 下の表のとおり。討論者の一覧とは別に、ApiStackがLambdaの環境変数で渡す。画面は `GET /models` で受け取る | 確定 |
| 既定のモデル | Claude Opus 4.6(`03-engine`「動作確認用のモデルの組み合わせ」の審判と同じ) | 確定 |
| 入れる条件 | 審判として議論を判定させ、判定の理由を人が読んで確かめたもの。今は Claude Opus 4.6 だけ(→ `03-engine`「優劣判定」) | 確定 |
| 選び方 | 1つ選ぶと、審判の全員がそのモデルになる。観点ごとに別のモデルは選ばない | 確定 |

| 名前 | モデルID | 特徴(画面に出す1行) |
|---|---|---|
| Claude Opus 4.6 | `global.anthropic.claude-opus-4-6-v1` | 議論を深く読み比べる。 |


- Haiku と Sonnet は `jp.` の推論プロファイルで、gpt-oss と Mistral Large 3 は東京リージョンで直接呼んで、日本国内で処理する。Opus は、このアカウントで呼べるのが `global.` の推論プロファイルだけのため、世界のどこかのリージョンで処理されることがある(討論者でも審判でも同じ)。選ぶときに特に必要な情報ではないため、カードの特徴の1行には書かない。

### `GET /models`

| 項目 | 内容 |
|---|---|
| 応答 | `{ "models": [モデル…], "judgeModels": [モデル…], "defaults": { "pro": "…", "con": "…", "judge": "…" } }` |
| モデル | `modelId`、`name`(表示用の名前)、`feature`(特徴の1行)。並びは上の表の順 |
| `judgeModels` | 審判で選べるモデル。形と並びは `models` と同じ |
| `defaults` | 先攻、後攻、審判の既定のモデルID |

### `GET /debates`

| 項目 | 内容 |
|---|---|
| クエリ | `limit`(1〜50、省略時20)、`cursor`(前回の応答の `nextCursor`。省略時は最初から) |
| 応答 | `{ "items": [議論の要約…], "nextCursor": "…" }`。続きがなければ `nextCursor` を持たない |
| 議論の要約 | `debateId`、`theme`、`positions`、`participants`(先攻と後攻のモデル。一覧に討論者のアイコンを出すため)、`status`、`maxTurns`、`createdAt`、`endReason`(あれば)、`concededBy`(あれば)、`winner`(判定の多数決の勝者。あれば) |
| 並び | `createdAt` の新しい順(GSI `byCreatedAt`) |
| 隠した議論 | 一般のユーザー(管理者でない人)には返さない。作った本人にも返さない。隠した議論を除いて `limit` 件まで集めて返す。管理者には隠した議論も返し、要約に `hidden: true` を付ける(→「議論を隠す」) |

- `cursor` は、DynamoDBの続きの位置を文字列にしたもの。中身に意味を持たせず、そのまま次の呼び出しに渡す。正しく読めない `cursor` は400を返す。

### `GET /debates/{debateId}`

| 項目 | 内容 |
|---|---|
| 応答 | `{ "debate": 議論, "messages": [発言…] }` |
| 議論 | Debatesの項目(`listKey` を除く)。判定結果 `verdict` を含む |
| 発言 | Messagesの項目を `turn` の順に並べたもの |
| 作戦メモ | 議論の `status` が `running` の間は、発言から `notes` を除いて返す。作戦メモは議論の終了後に開示するため(→ `03-engine`「作戦メモ」) |
| ない場合 | 404 |
| 隠した議論 | 一般のユーザーには、ない場合と同じ404を返す(隠した議論があることもわからないようにする)。管理者には返す |

### `PATCH /debates/{debateId}`

管理者が、議論を一般のユーザーに見せるか隠すかを切り替える。元に戻せる。

| 項目 | 内容 |
|---|---|
| だれができるか | 管理者だけ(→「認証」の「管理者」)。アクセストークンの `cognito:groups` に `admin` がなければ403 |
| 本文 | `{ "hidden": true }`(隠す)か `{ "hidden": false }`(見せる)。`hidden` が真偽値でなければ400 |
| 切り替えられる議論 | すべて(議論中の議論も) |
| 保存 | Debates の行の `hidden` を更新する(隠すときは `true`、見せるときは属性を消す) |
| 応答 | 204(本文なし) |
| ない場合 | 404 |

- 切り替えたことは、ログに残す(議論ID、`hidden`、切り替えた人の `sub`)。
- Debates の行が変わるため、購読している人に `debate` が配信される(→「WebSocket API」)。

### `DELETE /debates/{debateId}`

管理者が、議論を消す。消したものは元に戻せない。

| 項目 | 内容 |
|---|---|
| だれができるか | 管理者だけ(→「認証」の「管理者」)。アクセストークンの `cognito:groups` に `admin` がなければ403 |
| 消せる議論 | 終わった議論(`status` が `done` か `failed`)だけ。`running` の議論は409(エンジンが動いている途中のため) |
| 消すもの | Messages のその議論の発言をすべて消してから、Debates の行を消す(発言が残ったまま議論だけが消えることのないよう、この順にする)。途中で失敗したら500を返し、もう一度呼べば続きから消せる |
| 応答 | 204(本文なし) |
| ない場合 | 404 |

- 消したことは、ログに残す(議論ID、消した人の `sub`、消した発言の件数)。
- 消しても配信はしない(配信は、Messages の追加と Debates の更新だけを扱う。→「WebSocket API」)。

### `GET /accounts`

管理者が、アカウントの一覧を見る(→「アカウントの一覧」)。

| 項目 | 内容 |
|---|---|
| だれができるか | 管理者だけ(→「認証」の「管理者」)。アクセストークンの `cognito:groups` に `admin` がなければ403 |
| 読むもの | Cognito のユーザープールのすべてのユーザー(`ListUsers`)と、グループ `admin`・`demo` に入っているユーザー(`ListUsersInGroup`) |
| 応答 | `{ "items": [{ "email": "…", "type": "admin" \| "general" \| "demo", "enabled": true, "createdAt": "…" }] }`。`type` はアカウントの種類(→「アカウントの種類」)、`enabled` は使えるか(ログインのロックで止めたユーザーは `false`)、`createdAt` はユーザーを作った時刻 |
| 並び | `createdAt` の古い順 |
| 件数 | すべて返す(ページに分けない。この規模では数件のため) |

| 状態 | 本文 |
|---|---|
| 400 | `{ "message": "…", "errors": ["…"] }`(`errors` は検証の違反の一覧。あれば。画面にそのまま出すので、項目の名前は日本語で書く(例:「テーマは3〜200文字にしてください」「先攻の立場に改行・タブ・目に見えない文字は使えません」)。`theme` などの英語の項目名は出さない) |
| 401 | API Gatewayが返す |
| 403 | `{ "message": "…" }`(管理者だけができる操作を、管理者でない人が呼んだ) |
| 404 | `{ "message": "…" }` |
| 409 | `{ "message": "…" }`(実行中の議論があって作れない、実行中の議論は消せない) |
| 429 | `{ "message": "…" }`(デモのアカウントが、1日に作れる議論の数に達した) |
| 500 | `{ "message": "…" }`。内部の詳細は返さず、ログに残す |
| 503 | `{ "message": "…" }`(議論の作成で、入力の内容を確かめられなかった) |

## WebSocket API

| 項目 | 内容 |
|---|---|
| 接続 | `wss://…/<ステージ>?token=<Cognitoのアクセストークン>`。ブラウザはハンドシェイクにヘッダーを付けられないため、クエリで渡す |
| 本文 | JSON(UTF-8)。ブラウザからは `action` で、サーバーからは `type` で種類を示す |
| 購読の数 | 1つの接続で購読できる議論は1件。別の議論を購読すると置き換える |

### ルート(ブラウザ → サーバー)

| ルート | 本文 | 処理 |
|---|---|---|
| `$connect` | なし | クエリの `token` を、Lambdaのオーソライザーで検証する(→「認証」)。通ったら、Connectionsに接続ID・ユーザーID(`sub`)・`ttl` を保存する |
| `subscribe` | `{ "action": "subscribe", "debateId": "…" }` | 議論が存在すれば、接続に議論IDを紐付け、`subscribed` を返す。存在しなければ `error` を返す。隠した議論は、管理者でなければ存在しない場合と同じ `error` を返す(→「議論を隠す」) |
| `ping` | `{ "action": "ping" }` | 何もしない。無通信で10分たつと切断されるのを防ぐため、ブラウザが5分ごとに送る |
| `$disconnect` | なし | Connectionsから接続を消す |
| `$default` | ほかの本文 | `error` を返す(`action` が誤っている、本文がJSONでない、など) |

### 配信するメッセージ(サーバー → ブラウザ)

| `type` | 本文 | いつ |
|---|---|---|
| `subscribed` | `{ "type": "subscribed", "debateId": "…" }` | `subscribe` が通ったとき |
| `message` | `{ "type": "message", "message": 発言 }` | Messagesに発言が保存されたとき(→ `01-architecture`「DynamoDB Streams」) |
| `debate` | `{ "type": "debate", "debate": 議論 }` | Debatesの項目が変わったとき(終了、判定の保存など) |
| `error` | `{ "type": "error", "message": "…" }` | 本文が読めない、`action` が誤っている、議論がない、など |

- `message` の発言は、作戦メモ(`notes`)を除いて送る。発言が保存されるのは議論の進行中だけで、作戦メモは議論の終了後に開示するため(→ `03-engine`「作戦メモ」)。
- `debate` の議論は、`GET /debates/{debateId}` の `debate` と同じ形(`listKey` を除く。判定結果 `verdict` を含む)。
- 画面は、`status` が `running` 以外の `debate` を受け取ったら、`GET /debates/{debateId}` を取り直して、作戦メモを含む全発言を得る。

### 再接続(画面で行う)

- 切断されたら、間隔を1秒、2秒、4秒…と倍に延ばして(最大30秒)つなぎ直す。つながったら、間隔を1秒に戻す。
- つなぎ直したら、「接続 → 購読 → 履歴取得」をやり直し、重複は `turn` で除く(→「時系列」)。
- 接続の最大寿命(2時間)で切れた場合も、同じようにつなぎ直す。

- Cognito(セルフサインアップ無効、ユーザーは手動作成)をHTTP APIとWebSocket APIの両方に適用する。
- WebSocketはトークンをクエリ文字列で渡し、`$connect` のLambdaオーソライザーで検証する。

| 項目 | 内容 |
|---|---|
| サインイン | メールアドレスとパスワード |
| ログイン画面 | Cognitoのマネージドログイン画面。SPAは自前のログイン画面を持たず、パスワードを扱わない |
| 方式 | OAuth 2.0 の認可コードと PKCE。アプリクライアントはクライアントシークレットを持たない |
| スコープ | `openid`、`email`、`profile` |
| コールバックとサインアウトのURL | 開発用の `http://localhost:5173/` と、CloudFrontのドメイン(HostingStack。`https://<ドメイン>/`) |
| ドメイン | Cognitoのドメイン(接頭辞は `agorawl-<AWSアカウントID>`。リージョン内で重複しないようにする) |
| ユーザーの作成 | 管理者がAWS CLIで作る(`aws cognito-idp admin-create-user` など)。種類を変えるのも AWS CLI で、グループに入れるか外す(→「アカウントの種類」) |
| 管理者 | Cognito のグループ `admin` に入っている人。グループは AuthStack が作る。人を入れるのは AWS CLI で行う(`aws cognito-idp admin-add-user-to-group --user-pool-id <ID> --username <メールアドレス> --group-name admin`)。入れた後は、ログインし直すとトークンに反映される。管理者だけができること: 議論を消す(→「議論を消す」)、議論を隠す(→「議論を隠す」)、アカウントの一覧を見る(→「アカウントの一覧」) |
| 管理者の見分け方 | API は、アクセストークンの `cognito:groups` に `admin` があるかで見分ける。WebSocket は、`$connect` のオーソライザーがアクセストークンから見分け、その結果を各ルートに渡す。画面は、IDトークンの `cognito:groups` で見分け、管理者にだけ操作を出す(画面の表示は目安で、断るのは API) |
| WebSocketのオーソライザー | `$connect` のLambdaオーソライザーが、アクセストークンをCognitoの公開鍵(JWKS)で検証する。署名、期限、`token_use` が `access`、`client_id` がアプリクライアントのIDであることを確かめる。通らなければ接続を拒む |
| 動作確認用のトークン | 画面なしで確かめるため、アプリクライアントで管理者用のパスワード認証(`ADMIN_USER_PASSWORD_AUTH`)も許可する。AWSの認証情報を持つ人だけが使える。動作確認用CLI(`tools/call-api`)が使う |
| SPAのログインの処理 | ライブラリ `oidc-client-ts` を使う(認可コードとPKCE、トークンの保管と更新)。セキュリティに関わる部分を自前で書かない |

### ログインのロック

管理者のアカウントで、パスワードを3回続けて間違えたユーザーを止め、管理者にメールで知らせる。止めたユーザーは、管理者が解除するまでログインできない。

Cognitoには、パスワードを間違えたときに呼ばれる仕組みがない。そこで、ログインしようとした回数を事前認証のLambdaで数え、成功したら事後認証のLambdaで0に戻す。残った回数が、続けて間違えた回数になる。

| 項目 | 内容 | 状態 |
|---|---|---|
| 対象 | 管理者のアカウントだけ(→「アカウントの種類」)。一般とデモのアカウントは、何回間違えても止めない(デモのパスワードは視聴者に公開するため、だれかがわざと間違えると、ほかの視聴者が使えなくなる) | 確定 |
| 回数の置き場所 | AuthStackのDynamoDBのテーブル LoginAttempts(PK: `userName`。Cognitoのユーザー名)。項目は `attempts`(数値)と `lockedAt`(止めた時刻) | 確定 |
| 事前認証のLambda | まず、ユーザーが `admin` グループに入っているかを確かめる(`AdminListGroupsForUser`)。入っていなければ、数えずにログインを続ける。確かめられなかったとき(エラー)は、管理者として数える。管理者なら、ログインしようとするたびに、`attempts` を1つ足す。足した後の値が4以上(3回続けて間違えた後のログイン)なら、ユーザーを無効にし(`AdminDisableUser`)、ログインを断る。存在しないユーザー名での試み(`userNotFound`)は数えない | 確定 |
| 事後認証のLambda | ログインに成功したら、その行を消す(`attempts` を0に戻す) | 確定 |
| 管理者への通知 | 止めたとき(`attempts` が4になったとき)に1回だけ、NotifyStackのトピックでメールを送る(→ `01-architecture`)。件名は `[Agorawl] ログインを止めました: <メールアドレス>`。本文は、メールアドレス、止めた時刻、解除のコマンド | 確定 |
| 断ったときの表示 | ログイン画面に「ログインできません。管理者に連絡してください」と出る(Cognitoが、Lambdaのエラーの文言を前後の決まった文と合わせて出す) | 確定 |
| 解除 | 管理者が開発用CLIで行う。`npm run unlock-user -- <メールアドレス>`。ユーザーを有効に戻し(`AdminEnableUser`)、LoginAttemptsの行を消す | 確定 |
| 通知が届く時点 | 3回目を間違えた時点ではなく、その後にログインしようとした時点。間違えた時点で呼ばれる仕組みがないため | 確定 |
| わざと間違えられた場合 | パスワードを知らない人でも、管理者のアカウントを3回間違えれば、そのユーザーを止められる。解除するまでログインできない | 確定 |
| 動作確認用のトークン | `tools/call-api` の管理者用のパスワード認証(`ADMIN_USER_PASSWORD_AUTH`)も、同じく数える | 確定 |

## 画面(SPA)

`app/web/`。React + Vite + TypeScript。画面の切り替えは `react-router`。

### 画面の一覧

| 画面 | パス | 内容 |
|---|---|---|
| 表紙 | ログインしていないときの、どのパスでも | 「AI言い合いバトル」の文字と「ログイン」ボタン(→「表紙」) |
| 議論の一覧 | `/` | 新しい順(`GET /debates`)。1件ごとに、テーマ、2つの立場、状態(議論中・終了・失敗)、作成日時。勝者は出さない(開く前に結果が分からないようにする)。見た目は議論の画面の見出しにそろえる(先攻と後攻を「VS」をはさんだ色の札で並べ、札の外側に討論者のアイコンを置き、状態・作成日時を小さな札にする。一覧に合わせて小さめにする。アイコンの直径は40px(スマートフォンの幅では32px))。読み込んだ件数を出す(続きがあれば「続きあり」)。画面の右下に、議論の画面と同じ移動のボタン(上向きの矢印と「先頭へ」、「一番下へ」と下向きの矢印。→「矢印」)を置く。管理者には、終わった議論のカードの右上に「削除」ボタンを出す(→「議論を消す」)。管理者には、すべてのカードの右上に「隠す」か「見せる」のボタンを出し、隠した議論のカードに「非公開」の札を出す(→「議論を隠す」)。終了した議論のカードには、状態の札の右隣に「この設定で作る」を出す(→「設定を写して作る」)。カードのどこを押しても議論の画面へ移る(「削除」と「この設定で作る」を除く)。見出しの行(「議論の一覧」と件数、「議論を始める」)は画面の上に固定し、一覧だけをスクロールさせる。下まで読むと続きを読む(`nextCursor`)。議論の作成への入口を置く |

| 議論の画面 | `/debates/{debateId}` | 発言をターン順に並べる(→「議論の画面」) |
| アカウントの一覧 | `/accounts` | 管理者だけ。アカウントの一覧(→「アカウントの一覧」) |
| ログイン後の戻り先 | `/`(コールバック) | Cognitoから戻ったら、トークンを受け取り、ログインの前に開いていた画面へ戻る |

- 立場の名前(`positions`)を持たない古い議論(賛成・反対の形だったころのもの)は、先攻を「賛成」、後攻を「反対」として出す。
- 画面の一部で処理が止まっても、画面全体を真っ白にせず、「表示できませんでした」と一覧へ戻る案内を出す。
- ログインしていなければ、どの画面のURLを開いても、そのURLのまま表紙を出す(→「表紙」)。表紙の「ログイン」から、Cognitoのログイン画面へ移る。自前のログイン画面は持たない(→「認証」)。

- アクセストークンは `oidc-client-ts` が保管し、期限が近づいたら更新する。HTTP APIの `Authorization` とWebSocketのクエリ `token` に、同じアクセストークンを使う。

| 出す人 | 管理者だけ(→「認証」の「管理者」) |
| 置き場所 | 議論の一覧のカードの右上の、「削除」の左隣。見せている議論には「隠す」、隠している議論には「見せる」を出す。議論中の議論にも出す。議論の画面には置かない |

| 中身 | `GET /accounts` の表。1行に、メールアドレス、種類(管理者・一般・デモ)、状態(使える・止めている)、作った日(日本時間の年月日) |
| 並び | 作った日の古い順 |
| 管理者でない人が `/accounts` を開いたとき | API の403の文言(「アカウントの一覧を見られるのは管理者だけです」)を出す |
| 失敗したとき | 表の上にエラーの文を出す(APIの `message`) |

### 設定を写して作る

すでにある議論の設定を下書きにして、変えてから新しい議論として作る。元の議論は変えない。

| 項目 | 内容 |
|---|---|
| だれができるか | ログインした人全員 |
| 入口 | 議論の一覧の、終了した議論(`status` が `done`)のカードの、状態の札の右隣の「この設定で作る」。議論中と失敗のカードには出さない。議論の画面には置かない |
| 開く画面 | 作成の画面(`/new?from={debateId}`)。その議論(`GET /debates/{debateId}`)を読み込み、設定を入れる。読み込めなければ、空の作成の画面のまま、エラーの文を出す |
| 写すもの | テーマ、先攻と後攻の立場の名前(立場の名前を持たない古い議論は「賛成」「反対」)、先攻と後攻の討論者のAI、審判のAI(1人目の審判のモデル)、ターン数 |
| 写せないとき | 討論者や審判のAIが今は選べないモデル(選べるモデルの一覧にない)なら、その欄は既定のAIにする。ターン数が選べない数(4〜10の偶数でない)なら、既定のターン数にする。どちらも、写せなかったことを作成の画面の上に出す(例:「元の先攻のAI(…)は今は選べないため、既定のAIにしました」) |
| 画面の上の案内 | 「「<元のテーマ>」の設定を写しました。変えてから「議論を始める」を押してください」 |
| 先攻と後攻の入れ替え | 置かない |

### 表紙

ログインの前に見せる画面。AIが言い合うサービスであることを、文字の動きで見せる。

```
┌───────────────────────────────┐
│  (背景の模様)               バトル │
│                       言い合い        │
│                 AI                    │
│                                       │
│              [ ログイン ]             │
└───────────────────────────────┘
```

| 項目 | 内容 |
|---|---|
| 出すとき | ログインしていない人が、どの画面のURLを開いても、そのURLのまま出す。ログイン済みの人には出さない |
| 中身 | 背景の模様(→「背景」)、「AI言い合いバトル」の文字、「ログイン」ボタンだけ。画面上の見出しの行(メールアドレスとサインアウト)は出さない。APIは呼ばない |
| 文字 | 「AI言い合いバトル」を1行で、左下から右上へ16°傾けて、画面の真ん中に大きく出す。「AI言い合い」は先攻の色、「バトル」は後攻の色。太いゴシック(Dela Gothic One)で、白い縁取りと薄い影を付ける。大きさは画面の幅に合わせる(幅の11%、高さの16%の小さいほう) |
| 文字の動き | 1字ずつ、左下の外から大きく傾いた状態で飛び込み、少し行き過ぎて止まる。1字0.32秒、0.16秒ずつずらす(8字で約1.6秒) |
| ログインのボタン | 文字の下に置く。文字がそろった後(約1.9秒後)に、0.6秒で浮かび上がる。押すと、Cognitoのログイン画面へ移る。ログインした後は、表紙を開いたときのURLの画面に戻る |
| 動きを減らす設定 | 端末の設定で動きを減らしている人(`prefers-reduced-motion`)には、文字とボタンを最初から出す |
| 読み上げ | 文字は見出し(「AI言い合いバトル」)として読ませる。1字ずつの要素は読ませない |
| フォント | Dela Gothic One(SIL Open Font License 1.1)から、「AI言い合いバトル」の8字だけを切り出したファイル(WOFF2)を、画面と一緒に置く(`/fonts/`)。外のサービス(Google Fonts)からは読み込まない。権利の文面(`OFL.txt`)も同じ場所に置く。文字を変えたら、切り出し直す |

### AIを選ぶ

議論の作成の画面で、先攻と後攻の討論者のAIと、審判のAIを選ぶ。

| 項目 | 内容 |
|---|---|
| 作成の画面での表示 | 立場の欄の下に、先攻と後攻の欄を左右に並べる(スマートフォンの幅でも左右に並べる)。それぞれに、その側の色の枠で、選んでいるAIの正面の立ち姿(画面用に縮めた版 `/characters/<ID>-front-sm.png`。→ `05-persona-illustration`「ポーズ」)、名前、性能の星(→「発言のアイコン」)、「AIを選ぶ」ボタンを出す。立ち姿の高さは180px(スマートフォンの幅では120px)。初めは既定のモデル(`GET /models` の `defaults`)を出す |
| 一覧の読み込み | 作成の画面を開いたら `GET /models` を呼ぶ。読み込めなければ「AIの一覧を読み込めませんでした。既定のAIで始めます」と出し、`models` を送らずに作れるようにする |
| 選ぶ画面を開く | 「AIを選ぶ」を押すと、カットインと同じ暗い色で画面全体を覆い、選べるAIのカードを出す。上に「先攻のAIを選ぶ」(後攻なら「後攻のAIを選ぶ」)を、その側の色で出す。カードは、先攻なら左の外から、後攻なら右の外から、0.3秒で滑り込む(カードごとに0.05秒ずつずらす)。スマートフォンの幅(600px以下)では、カードを横に動かさず、下から少し浮き上がって出す(横にめくる枠の中でカードを横に動かすと、スマートフォンのブラウザで、めくる位置がずれてカードが隠れることがあるため。審判のカードも同じ) |
| カード | 正面の立ち姿(高さ220px。スマートフォンの幅では180px)、名前、性能の星、特徴の1行(`GET /models` の `feature`)、「このAIにする」ボタン。今選んでいるAIのカードには「選択中」の札を出す。同じグループのAI(Claude の Haiku、Sonnet、Opus)は、同じ立ち姿になり、星と特徴で見分ける |
| キャラクターの説明 | カードをグループ(キャラクター)ごとにまとめ、グループのカードの列のすぐ下に、そのグループの説明を1つ出す。中身は、AI自身に聞いた答えのモチーフと性格の3語(→ `05-persona-illustration`「見た目をAIに聞く」)と、それを選んだ理由を画面用に短くした文。見出し「<グループの名前>のキャラクター」を付けた白い枠で出す。グループは、`GET /models` の並びで最初に出てくる順に並べる。立ち絵のないモデルは、説明のないグループにまとめて最後に置く。答えは同じグループのAIで同じなので、カードごとには出さない |
| 理由の文 | Claude: 「知識や議論に関連した賢さの象徴であり、大きな目は異なる視点をじっくり観察するため」。OpenAI: 「腕がたくさんあるので議論のポイントを指し示したり、情報を同時に扱える点が討論者にぴったり」。Mistral: 「電球はAIのひらめきを表し、ペンギンの体型で親しみやすく、知性とユーモアを兼ね備えた議論好き」。答え(`answers/<ID>.json`)そのものは変えない |
| 文字の濃さ | 暗い覆いの上の白い枠(カードとキャラクターの説明)の文字は、本文と同じ濃さ(`--text`)にする |
| 並び | グループごとに、PCの幅では横に並べ、入りきらなければ折り返す。スマートフォンの幅(600px以下)では横に1列に並べ、横にめくる(1枚ずつ止まる) |
| 選ぶ | 「このAIにする」を押すと、選ぶ画面を閉じ、作成の画面のその側に、選んだAIを出す |
| 選ばずに閉じる | 右上の「閉じる」、カードの外の暗い部分を押す、Escキーのどれかで閉じる。選んでいたAIは変わらない |
| 動きを減らす設定 | 端末の設定で動きを減らしている人(`prefers-reduced-motion`)には、滑り込む動きを付けずに出す |
| 読み上げ | 選ぶ画面はダイアログ(`role="dialog"`)とし、開いたら1枚目のカードの「このAIにする」に移る。閉じたら、押した「AIを選ぶ」に戻る |
| 絵のないモデル | 立ち姿の場所を空けて、名前と特徴だけを出す(今の選べるモデルには、絵のないモデルはない) |

審判のAIを選ぶ(討論者と同じ作りにし、違うところだけを書く):

| 項目 | 内容 |
|---|---|
| 審判の欄 | 先攻と後攻の欄の下に、横幅いっぱいの「審判」の欄を置く。中身は討論者の欄と同じ(立ち姿、名前、星、「AIを選ぶ」)。立ち姿は、モデルによらず審判の絵(`/characters/judge-front-sm.png`)。立ち姿の上に、観点の持ち物の印(天秤、虫めがね、盾と旗。→「判定の節」)を3つ横に並べる(3人が別々の観点で判定することを見せるため)。名前の下に「3人(論理、根拠、反論・応答)で判定」と出す。初めは既定の審判のモデル(`GET /models` の `defaults.judge`)を出す |
| 色 | 審判の色(ハリネズミに合わせた茶色)。欄の枠、札、選ぶ画面の見出し、「選択中」の札に使う |
| 選ぶ画面 | 見出しは「審判のAIを選ぶ」。カードは `judgeModels` を出し、下から滑り込む。カードの立ち姿は審判の絵。観点の印は出さない(選ぶ画面はモデルを選ぶ場所のため) |
| キャラクターの説明 | 見出し「審判のキャラクター」。ハリネズミ(公正・辛口・愛嬌がある)と、理由の文「針で鋭く論点を突く審判で、丸くてコミカルな体型」(審判に聞いた答え `answers/judge.json` を画面用に短くした文) |
| 送るもの | `POST /debates` の `models.judge` に、選んだモデルIDを送る |

### 議論の画面

| 項目 | 内容 |
|---|---|
| 見出し | テーマ、先攻と後攻の立場の名前、状態(議論中・終了・失敗)、ターン数、作成日時。まとめて1つの枠で囲む。テーマは大きく太く出す。先攻と後攻は、それぞれの色の札(「先攻」「後攻」のラベル(その側の色で塗った小さな丸い札に、白い文字)と、立場の名前)を「VS」をはさんで左右に並べる。札の外側(先攻は左、後攻は右)に、討論者のアイコン(発言のアイコンと同じ丸。どの絵を出すかは、議論の `participants` の先攻と後攻のモデルIDで決める)を置く。状態・ターン数・作成日時は、小さな札にして並べる |
| カットイン | 議論の画面を開いたときに、「AI言い合いバトル」の文字、議論のテーマ、討論者の2人が向かい合って指さし合う演出を、画面の上に重ねて出す。見る人が押したら消して、議論のページを見せる(→「カットイン」) |
| 発言の並べ方 | チャットのような形。先攻の発言は左、後攻の発言は右に並べ、色を分ける。発言ごとに、ターンのラベル、立場の名前、本文、引用した資料の番号。ターンのラベルは、ターンと段階(立論・攻防・投了)を書いた札の形にし(例:「ターン1・立論」)、先攻と後攻で色を分ける。投了・引き分けの発言には印を付ける |
| 届いた発言 | WebSocketで届いた発言(`message`)を下に足す。`turn` で重複を除き、`turn` の順に並べる。発言が届いても、画面はスクロールさせない(読んでいる途中で動かさない。進行中の議論を開いたときも、上から見せる)。代わりに「新しい発言の知らせ」を出す |
| 新しい発言の知らせ | 議論の画面を開いた後に届いた発言が、まだ画面に入っていなければ、画面の下の真ん中に「ターン6が届きました」と下向きの矢印(→「矢印」)のボタンを出す。2件以上たまったら「ターン6〜7が届きました」とする。押すと、まだ見ていない発言のうち最も古いもの(この例ではターン6)まで、スクロールしながら移る(動きを減らす設定の人には動かさずに移す)。届いた発言が画面に入ったら(押して移ったときも、自分でスクロールしたときも)、そこまでを見たことにし、見ていない発言がなくなったらボタンを消す |
| 進行中 | 「議論中」と、次の発言を待っていることを表示する |
| 終了 | `status` が `running` 以外の `debate` を受け取ったら、`GET /debates/{debateId}` を取り直す(作戦メモを含む全発言と判定を得る)。終了理由と勝者は、「結果」の節に出す(→「結果の節」) |
| 発言のアイコン | 発言の横に、発言したモデルの立ち絵の頭から胸のあたりを、丸いアイコンにして出す(証明写真のように)。直径は56px(スマートフォンの幅では40px)。背景と枠は、先攻と後攻の色。どの絵を出すかは、発言のモデルID(`modelId`)で決める(`anthropic.` を含めば Claude、`openai.` を含めば OpenAI、`mistral.` を含めば Mistral)。立ち絵のないモデルは、空の丸にする。画像は、立ち絵から作ったアイコン用の小さな画像(`/characters/<ID>-icon.png`)を使う(→ `05-persona-illustration`「アイコン」)。丸の上端に、モデルの性能を表す小さな金色の星(★)を、少しかぶせて重ねる。星の数の決め方は `05-persona-illustration`「立ち絵」の「星の付け方」。星のないモデルには出さない。議論の画面の見出しと一覧のカードのアイコンにも出す。カットインの絵には出さない |
| 引用 | 発言の「引用」の番号を押すと、画面の上に窓(モーダル)が開き、資料の中身(検索語、事実の要約、出典のURL、どちらがどのターンで調べたか)を出す。「閉じる」ボタン、窓の外を押す、Escキーのどれかで閉じ、読んでいた位置にそのまま戻る。ページの並びは変えない。発言の本文の中に出てくる資料の番号(「[3]によれば…」など)も、同じく押すと窓で資料を出す。資料一覧にない番号(`invalidCitations`)には「資料一覧にない番号」と印を付ける |
| 資料一覧 | 発言の下(判定の節の前)に「資料一覧」の節を置く。初めは閉じておき、「資料一覧(○件)を開く」を押したときだけ、議論で集めたすべての資料を番号順に並べる(→「資料一覧の節」)。ページが長くならないようにするため。議論の進行中も出す。資料は両者と審判が読む共有のもので、内緒のものではないため |
| 作戦メモ | 議論の終了後だけ、発言ごとに「作戦メモ」を開くボタンを付ける。押すと、その発言の時点の主張一覧と反論一覧(ID、内容、点数、状態。反論は対象も)が開く。進行中は出さない(APIも返さない → 「HTTP API」)。上に、IDの説明(→「判定の節」)を置く |
| 結果と判定 | 議論が終わったら、資料一覧の下に、「結果」の節(見出し「議論が終わりました」。→「結果の節」)、「判定の内訳」の節(→「判定の節」)、「項目ごとの点数」の節(→「判定の節」)の順に置く。判定がない議論は、結果の節だけ。結果の節へは、移動のボタン(下の行)で移る |
| 移動のボタン | 画面が長いため、画面の右下に常に出るボタンを置き、どの位置からでも移れるようにする。上向きの矢印と「先頭へ」(ページの先頭へ)と、議論が終わっていれば「結果へ」と下向きの矢印(結果の節へ)。矢印の形は「矢印」に従う。移るときは、いきなり飛ばずに、スクロールしながら動かす。ただし、端末の設定で動きを減らしている人(`prefers-reduced-motion`)には、動かさずに移す |

#### 結果の節

議論が終わったときに、先攻と後攻の2羽の絵で、勝ち負けを見せる。

```
┌──────────── 議論が終わりました ────────────┐
│        終了理由: 最大ターン数に到達             │
│        熊派の勝ち(審判3人のうち2人)            │
│     [落ち込む絵]              [喜ぶ絵]          │
│    (先攻)虎派  負け        (後攻)熊派  勝ち    │
└─────────────────────────────────┘
```

| 項目 | 内容 |
|---|---|
| 見出し | 「議論が終わりました」(失敗は「議論は途中で止まりました」) |
| 結果の文 | 判定があれば多数決の結果(例:「熊派の勝ち(審判3人のうち2人)」)。審判の人数の部分(「(審判3人のうち2人)」「(審判3人の判定が分かれた)」)は、改行して2行目に出す。判定がなければ、投了は「虎派の勝ち(投了)」、両者の攻め手が尽きたら「引き分け」 |
| 絵 | 先攻を左、後攻を右に並べる。絵は、討論者のポーズの絵の縮めた版(`/characters/<ID>-<ポーズ>-sm.png`)。後攻は左右を反転して、向かい合わせる。高さは200px(スマートフォンの幅では140px)。立場の名前の長さで札の高さが違っても、2羽の絵の位置(上下)はそろえる |
| 絵の下 | その側の立場の名前の札(「先攻」「後攻」のラベル付き)と、「勝ち」「負け」「引き分け」の札。勝った側の名前の札は、金色の縁にする。「勝ち」「負け」「引き分け」は、判定の内訳の勝者の帯と同じ形の帯(太字)にし、名前の札と同じ幅にする。「勝ち」はその側の色(先攻はオレンジ、後攻は青)に白い字、「負け」「引き分け」は薄い灰色に濃い灰色の字にする。立場の名前の長さが違っても、先攻と後攻で、絵、名前の札の枠(高さも)、「勝ち」「負け」の札の位置を横にそろえる。絵のない側も、絵の分の高さを空けてそろえる |
| 終了理由 | 見出しのすぐ下に「終了理由: …」。文字の大きさと太さは見出しと同じ |
| 勝った側の動き | 結果の節が画面に入ったときに、勝った側の絵が1回飛び跳ね、「勝ち」の帯が小さい状態から弾んで出る。動きを減らす設定の人(`prefers-reduced-motion`)には動かさない |
| 絵のないモデル | その側は、絵を出さず、札だけ |

終わり方ごとのポーズ:

| 終わり方 | 先攻と後攻のポーズ |
|---|---|
| 判定で勝ち負けが決まった | 勝った側は「勝って喜ぶ」(`win`)、負けた側は「負けて落ち込む」(`lose`) |
| 投了 | 投了した側は `lose`、相手は `win` |
| 引き分け(判定の引き分け、両者の攻め手が尽きた) | 両方「考え込む」(`think`)。文字は両方「引き分け」 |
| 判定を待っている(最大ターン数で終わり、判定がまだない) | 両方 `think`。「勝ち」「負け」の文字は出さず、「判定を待っています…」と出す |
| 失敗(途中で止まった) | 絵と札を出さず、見出しと終了理由だけ |

#### カットイン

| 項目 | 内容 |
|---|---|
| 出すとき | 議論の画面を開くたびに出す(一覧からのクリック、議論の作成後の移動、URLを直接開く、再読み込みのどれでも) |
| 出す前 | 開いたらすぐ画面全体を暗い色で覆い、議論(`GET /debates/{debateId}`)と絵を読み込む。読み込み終わってから再生する。どのキャラクターの絵を出すかは、議論の `participants` の先攻と後攻のモデルIDで決める(決め方は発言のアイコンと同じ) |
| 絵 | 討論者の「右を指さして言い合う」ポーズの、画面用に縮めた絵(`/characters/<ID>-debate-sm.png`。→ `05-persona-illustration`「ポーズ」)。先攻はそのまま(右向き)、後攻は左右を反転して(左向き)出す。同じキャラクター同士でも、同じ絵を反転して使う。それぞれの絵の下に、その側の立場の名前を、先攻と後攻の色の札で出す。立場の名前の長さで札の行数が違っても、2人の絵の位置(上下)はそろえる |
| 並べ方 | 上から、「AI言い合いバトル」の文字、議論のテーマ、2人の絵と「VS」、「TAP TO START」(または「CLICK TO START」)の順に、画面の真ん中に並べる |
| 「AI言い合いバトル」の文字 | 表紙と同じ見た目(太いゴシック、「AI言い合い」は先攻の色、「バトル」は後攻の色、白い縁取り。→「表紙」)。傾けずに1行で出す。大きさは画面の幅に合わせる(幅の7%、最大3rem) |
| 議論のテーマ | 「AI言い合いバトル」の下に、白い太字で、かぎかっこ(「」)で囲んで出す。長いテーマは折り返す(最大3行。それより長いと末尾を「…」で切る) |
| 流れ | 0〜0.3秒: 「AI言い合いバトル」とテーマが上から降りてくる。同時に、先攻の絵が左の外から、後攻の絵が右の外から滑り込む。0.3〜0.5秒: 真ん中に「VS」が弾むように出る。0.8秒: 「TAP TO START」が出て、ゆっくり点滅を続ける。そのあとは、見る人が押すまで止めたままにする(時間では消さない) |
| 「TAP TO START」の文字 | タッチで操作する端末(指で触る画面。`pointer: coarse`)では「TAP TO START」、マウスの端末では「CLICK TO START」と出す |
| 消す | 画面のどこかを押すか、キーボードの Enter・スペース・Esc で、覆いごと0.3秒で消して議論のページを見せる。「TAP TO START」は、読み上げとキーボードでも押せるボタンにする(開いたときに、そのボタンに入力を向ける) |
| 大きさ | 絵の高さは、画面の高さの38%(最大320px)。スマートフォンの幅では、2人と「VS」が横に収まる大きさに縮める |
| 動きを減らす設定 | 端末の設定で動きを減らしている人(`prefers-reduced-motion`)には出さない |
| 絵のないモデル | 両方とも絵がないときは出さない。片方だけないときは、その側に立場の札だけを出す |
| 読み込めないとき | 議論を読み込めなかったとき(404など)は出さず、今のエラーの表示にする |

- 開いたときは「接続 → 購読 → 履歴取得」の順に行う(→「時系列」)。切断されたら、再接続の方式(→「WebSocket API」)でつなぎ直す。5分ごとに `ping` を送る。

### 資料一覧の節

- 資料は、各発言の `sources`(→ `02-data-model`「Messagesの `sources`」)を、資料の番号の順に並べたもの。APIの `GET /debates/{debateId}` の発言と、WebSocketで届く発言に含まれている。
- 1件ごとに、番号、検索語、どちらがどのターンで調べたか、事実の要約、出典のURL(リンク)を出す。
- 要約は、検索用のモデルがまとめたもので、元のページの本文ではない(→ `03-engine`「Web検索と資料一覧」)。その旨を節の上に書く。

### 判定の節

見る人の楽しみは、勝ち負けをどう判断したかを見ること(→ `00-overview`「目的」)。審判ごとの見方の違いが分かるように並べる。1と2は「判定の内訳」の節、3は「項目ごとの点数」の節に分け、結果の節の下に、この順で置く。

| 順 | 中身 |
|---|---|
| 1 | 判定の説明の文。審判が何で採点し、どの審判がどちらを選び、多数決でどうなったか(例:「審判3人が、両者を4項目(論理・根拠・反論・応答。各0〜10点、合計40点)で採点し、それぞれ勝者を選びました。熊派を選んだのは2人(審判1・審判3)、虎派を選んだのは1人(審判2)です。過半数の審判が選んだ熊派の勝ちです。」)。選んだ人がいない側は書かず、引き分けとした審判がいれば「引き分けとしたのは…」を足す。過半数が同じ側を選ばなかったら「過半数の審判が同じ側を選ばなかったため、引き分けです。」、過半数が引き分けとしたら「過半数の審判が引き分けとしたため、引き分けです。」。審判が1人なら「審判1人が、両者を4項目(…)で採点し、熊派を勝者に選びました。」。すべての審判に観点があれば、最初の文を「審判3人が、それぞれ別の観点(審判1は論理、審判2は根拠、審判3は反論・応答)から、両者を4項目(…)で採点し、それぞれ勝者を選びました。」とする。すべての審判が重み(`weights`)を持てば、項目の説明から「合計40点」を除き、「…で採点し、観点の項目の点を2倍にして合計し、それぞれ勝者を選びました。」とする。多数決の勝者がない古い判定は、最後の文を出さない。多数決の結果の短い文(「熊派の勝ち(審判3人のうち2人)」)は、結果の節に出す |
| 2 | 審判ごとの判定。審判1人を1枚のカードにして並べる(画面の幅が800px以下では縦に並べる)。カードには、審判の絵、審判の名前、観点の説明(観点がある審判のみ。例:「主張と理由の筋道、前の発言との矛盾を特に注意して見る」)、勝者、両者の合計点を出す。4項目の点数(論理・根拠・反論・応答。重みが2の項目は「根拠 7×2」のように出す)と両者への理由は、初めは閉じておき、カードごとの「詳しく見る」を押したときだけ開く。勝者は、名前や観点の説明の下に1行で、勝った側の色(引き分けは審判の色)で塗った帯に白い太字で出す(例:「フリーザ様の勝ち」)。カードを横に並べたときは、勝者の帯、先攻の合計点の行、後攻の合計点の行、「詳しく見る」の位置を、カードどうしで横にそろえる(名前や観点の説明の長さが違っても、勝者と点数を横に見比べられるようにする。その分、短いカードの上の部分に余白ができてよい)。「詳しく見る」で開いた中身(先攻と後攻の4項目の点数と理由)は、「閉じる」のボタンの下に出し、押したカードだけを伸ばす(ほかのカードの高さは変えない)。カードを横に並べるのは、画面の幅が800pxより広いときだけで、それ以下では縦に1列に並べる(途中で折り返して2枚と1枚に分けない) |
| 3 | 項目ごとの点数。先攻と後攻に分けた表で、1行が主張か反論1件。列は、種類とID(例:「主張 C1」「反論 R1」)、内容、討論者の点数、審判ごとの点数。討論者の状態(守る・捨てる、獲得・追及中・断念)の列は置かない(状態は、あとで点数の列にアイコンで示す。#48)。項目は、その側の最後の作戦メモにあるもの。節の見出し「項目ごとの点数」の下に「項目ごとの点数を開く」ボタンだけを置き、押したときだけ、先攻と後攻の表を開く(資料一覧と同じ形) |

- 審判の理由の文に出てくる資料の番号(`[3]` など)は、発言の引用と同じく、押すと窓(モーダル)で資料の中身を出す(→「議論の画面」の「引用」)。資料一覧にない番号は、ただの文字のままにする。
- 審判の理由の文に出てくる項目のID(「先攻C1」「後攻R2」など。審判は先攻・後攻を頭に付けたIDで書く。→ `03-engine`「プロンプト」の審判。「先攻R3・R9」のように「・」でつないだ2つめ以降は、頭を省いても同じ側のIDとする)は、資料の番号と同じ見た目で押せるようにし、押すと窓(モーダル)で項目の中身を出す。窓には、見出し(例:「ディオ様(先攻)の主張 C1」)、内容、反論なら対象、点数(討論者の点数と審判ごとの点数。例:「討論者 7 / 審判 6・7・8」。審判に渡していない項目の審判の点数は「-」)を出す。閉じ方は資料の窓と同じ。項目は「項目ごとの点数」の表と同じもの(その側の最後の作戦メモにあるもの)で、そこにないIDや、項目ごとの点数を持たない古い判定では、ただの文字のままにする。
- 審判の絵: カードの左上に、審判の正面の立ち姿の縮めた版(`/characters/judge-front-sm.png`)を全身で出す。高さは96px(スマートフォンの幅では72px)。名前と観点の説明は、絵の右に並べる。勝者は、絵の下に帯で出す(→ 上の表の2)。審判の絵はモデルによらず1つ(→ `05-persona-illustration`「立ち絵」)なので、観点のない審判や古い判定にも出す。絵は飾りとし、読み上げない(名前で伝わるため)。
- 観点の印: 観点がある審判は、絵の右上に、少しはみ出すように丸い印(`/characters/judge-mark-<観点>.png`)を重ねる(討論者の星と同じ置き方)。直径36px(スマートフォンの幅では28px)。論理は天秤、根拠は虫めがね、反論・応答は盾と交差した旗(→ `05-persona-illustration`「立ち絵」)。印は読み上げない(観点は名前で伝わるため)。
- 審判の名前は、番号とモデル名の両方を出す(例:「審判1(OpenAI gpt-oss-120b)」)。観点がある審判は、観点の名前も出す(例:「審判1 論理の審判(Claude Opus 4.6)」)。カードでは、番号と観点(「審判1 論理の審判」)と、モデル名(「(Claude Opus 4.6)」)を2行に分けて出す(モデル名の途中で改行しないため)。提供元ごとの見方の違いも見どころなので、モデル名を隠さない。モデル名は、モデルIDから表示用の名前に置き換える(知らないモデルIDは、そのまま出す)。
- 表の上に、IDの説明を置く:「C1、C2…は主張(自分の立場が良い理由)、R1、R2…は反論(相手の主張の弱さを突く指摘)。番号は先攻と後攻で別々に振る。」
- 同じIDの説明を、「判定の内訳」の節の、判定の説明の文と審判のカードの間にも置く(審判の理由の文にも C1、R1 などが出てくるため)。文字の大きさと色は、表の上の説明と同じ(小さく薄い文字)。
- 項目の内容が長いときは2行で切り、押すと全文を開く。項目の内容(項目ごとの点数の表とカード、作戦メモ、項目の窓)に出てくる資料の番号(`[3]` など)は、発言の引用と同じく押せるようにし、押すと窓で資料の中身を出す(→「議論の画面」の「引用」)。番号を押したときは、全文を開け閉めしない。資料一覧にない番号は、ただの文字のままにする。
- スマートフォンの幅(600px以下)では、項目ごとの点数を表ではなく1件ずつのカードにする。1行目に種類とID、討論者の点数、審判ごとの点数(例:「討論者 7 / 審判 3・6・2」)をまとめ、2行目から内容を画面の幅いっぱいに出す。表のままだと、内容の列が狭くなり、縦に長くなるため。
- 審判に渡していない項目(議論の最後の発言で初めて足した反論。→ `03-engine`「項目ごとの採点」)の審判の点数は「-」とする。
- 判定がない議論(投了・引き分けで終わった、判定の前に止まった)は、判定の節を出さず、結果の節だけを出す(→「結果の節」)。
- 項目ごとの採点や多数決を加える前に判定した議論は、ある項目だけを出す(多数決の勝者がなければ、審判1人の勝者を出す。項目ごとの点数がなければ、その表を出さない)。

### 見た目

- 簡素で読みやすい見た目にする。色は、先攻と後攻で2色に分ける。
- スマートフォンの幅でも崩れないようにする。
- CSSはライブラリを使わずに書く(部品が少なく、依存を増やさないため)。

#### 背景

| 項目 | 内容 |
|---|---|
| 模様 | 「Agorawl」の文字を、左下から右上へ斜めに傾けて、画面いっぱいに繰り返し並べる。行ごとに、先攻の色と後攻の色を交互にし、行ごとに半分ずらす(レンガ積み) |
| 濃さ | うっすら見える濃さ。どの画面も同じにする |
| 動き | 背景は画面に固定し、スクロールしても動かさない |
| 範囲 | SPAの画面だけ。Cognitoのログイン画面(マネージドログイン)は標準のまま |

- 模様は、文字を描いた小さなSVGをCSSで敷き詰めて作る(画像ファイルもJavaScriptも使わない)。
- 一覧の上に固定した見出しの行は、背景の模様が透けて見えるよう、半透明にしてぼかす。

#### 矢印

| 項目 | 内容 |
|---|---|
| 使う場所 | 議論の画面の左上の「一覧へ」(左向き)、移動のボタンの「先頭へ」(上向き)・「結果へ」(下向き)・一覧の「一番下へ」(下向き) |
| 形 | 太く塗った矢印(三角の頭と、太い軸)。文字(「←」「↑」など)では出さない。文字の矢印は、端末のフォントによって形や色(絵文字のように色が付くなど)が変わるため |
| 作り方 | 小さなSVGを画面のコードの中に持ち、文字の色で塗る(画像ファイルは使わない)。大きさは隣の文字に合わせる |
| 並べ方 | 矢印は文字の横に置く。行き先が上か左なら文字の前、下なら文字の後ろ(「先頭へ」は矢印が前、「結果へ」「一番下へ」は矢印が後ろ)。どの画面でも同じ決まりにする |

### 設定(`config.json`)

SPAは、起動時に `/config.json` を読んで、つなぎ先を知る。WebStackがデプロイのときに作って、SPAと一緒に置く。ビルドを環境ごとにやり直さずに済むようにするため。

```json
{
  "apiUrl": "https://….execute-api.ap-northeast-1.amazonaws.com",
  "webSocketUrl": "wss://….execute-api.ap-northeast-1.amazonaws.com/prod",
  "cognito": { "authority": "https://cognito-idp.ap-northeast-1.amazonaws.com/<ユーザープールID>", "domain": "https://agorawl-….auth.ap-northeast-1.amazoncognito.com", "clientId": "…" }
}
```

- 開発用(`npm run dev`、`http://localhost:5173`)では、`app/web/public/config.json` を手元で作って使う(コミットしない)。
- ログイン後の戻り先とサインアウト後の戻り先は、開いているページのオリジン(`https://<CloudFrontのドメイン>/` か `http://localhost:5173/`)とする。

### 配信(CloudFront)

| 項目 | 内容 |
|---|---|
| S3 | 非公開。CloudFrontだけが読める(オリジンアクセスコントロール) |
| 既定のページ | `index.html` |
| SPAのパス | S3にないパス(`/debates/…` など)は、`index.html` を返す(画面の切り替えはSPAが行う) |
| キャッシュ | `index.html` と `config.json` はキャッシュさせない(デプロイの後すぐに新しい版を使うため)。ビルドで名前にハッシュの付くファイルは、長くキャッシュさせる |
| HTTPS | CloudFrontの既定のドメイン(`….cloudfront.net`)と証明書を使う。独自のドメインは使わない |
