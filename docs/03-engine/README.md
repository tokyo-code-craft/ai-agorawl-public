## 役割と対戦

| 項目 | 内容 | 状態 |
|---|---|---|
| 役割 | 先攻(`pro`)、後攻(`con`)の2役。司会は置かない。議論のまとめは、審判の評価の理由が担う | 確定 |
| 立場 | 先攻と後攻は、議論ごとに指定する2つの立場(`positions`)をそれぞれ受け持つ(例:「週休3日制」と「週休2日制(現状維持)」)。賛否の形に限らず、2つの案を比べる形にする | 確定 |
| モデルの割当 | 先攻と後攻に別モデルを割り当てて対戦させることを基本とする(公開時の組み合わせ)。検証などのため、同じモデルも設定できる | 確定 |
| 判定役 | 先攻・後攻と同じモデルでもよい(→ `00-overview/decisions.md`) | 確定 |
| 人格 | 各モデルに人格を設定する(→ `05-persona-illustration`) | 確定 |

- 役割とモデルの対応は `participants` で、立場の名前は `positions` で設定する(→ `02-data-model`)。
- 賛否を問うテーマも、立場を「導入すべき」「導入すべきでない」のように書けば扱える。
- 審判の人格は薄くする(判定の中立性のため)。審判に持たせる観点(→「優劣判定」の「観点」)は、議論を読むときに特に注意するところで、人格(口調や好み)ではない。

## 進行

- 段階: 立論 → 攻防(守りと攻めを毎ターン両方行う)。
- 終了条件: 次のいずれか早いもの。議論は、そのターンの発言を保存したところで終える。
  - 最大ターン数(`maxTurns`。議論ごとに設定できる。4〜50の偶数)の発言をする。
  - 先攻か後攻が投了する(→「投了」)。
  - 両者の攻め手が尽きて引き分けになる(→「引き分け」)。
- 投了・引き分けは、まれに起きる終わり方とする。多くの議論は最大ターン数で終わり、その勝敗は審判が決める(→「優劣判定」)。

### ターンと段階・話者の対応

ターン数を N(`maxTurns`)とする。

| ターン | 話者 | 段階 | 内容 |
|---|---|---|---|
| 1 | 先攻(`pro`) | 立論 | 主張一覧を作り、主張を述べる。攻めはない |
| 2 | 後攻(`con`) | 立論 | 先攻の立論を見ずに、主張一覧を作り、主張を述べる。攻めはない |
| 3 | 先攻 | 攻防 | 自分の最初の攻防。後攻の立論を読んで反論一覧を作り、攻める。まだ反論を受けていないので守りはない |
| 4 | 後攻 | 攻防 | 自分の最初の攻防。先攻の反論に答え(守り)、先攻の立論への反論一覧を作って攻める |
| 5 〜 N | 先攻 → 後攻 の繰り返し | 攻防 | 相手の反論に答え(守り)、相手の主張を追及する(攻め)。一覧を更新する |

- 先攻と後攻は交互に発言し、常に先攻が先に発言する。最後の発言(ターンN)は後攻になる。
- 先攻と後攻の発言回数を同じにするため、N は偶数にする。
- 立論(ターン1・2)では、両者とも相手の主張を見ずに立論する。立論のターンのプロンプトには、それまでの発言も資料一覧も入れない(→ `prompts.md`)。攻防(ターン3〜)からは、全発言と全資料を渡す。
- 攻める回数は、先攻・後攻とも N/2 − 1 回で同じになる。
- 投了した側の発言は、段階を「投了」とする。
- 各ターンで前の発言履歴を次の発言の入力にする。
- 出力: 話者、モデル名、内容、ターン番号を発言ごとにMessagesへ保存する。先攻・後攻の発言には、作戦メモ、投了の有無、引き分けの有無も保存する。

### 作戦メモ(主張一覧と反論一覧)

先攻と後攻は、それぞれ自分の作戦メモを持ち、点数を稼ぐことを目指して議論する。

| 一覧 | 項目 | 点数(0〜10、整数)の意味 | 状態 |
|---|---|---|---|
| 主張一覧 | ID(`C1`…)、内容、点数、状態 | 議論の後に審判が付けるであろう、その主張の点数の見込み。審判は、その主張が相手の反論を受けてもどれだけ持ちこたえたかで付ける(相手の反論に根拠付きで答えられていれば高く、答えられていない反論(答える機会のない反論は除く)が残っていれば低い。→「項目ごとの採点」) | 守る(`defending`)/ 捨てる(`abandoned`)。モデルが決める |
| 反論一覧 | ID(`R1`…)、対象(相手のどの主張か)、内容、点数、状態 | その反論で相手をどれだけ崩せているか。相手がはぐらかした・根拠を示せなかったら高く、相手が根拠付きで直接答えたら低い。相手がまだ答えていない反論は見込みで付ける | 点数からエンジンが決める(下表) |

| 反論の点数 | 状態 | 扱い |
|---|---|---|
| 8以上 | 獲得(`won`) | ポイントを稼いだとして追及を終え、次の反論を探す |
| 4〜7 | 追及中(`pursuing`) | 追及を続ける |
| 3以下 | 断念(`dropped`) | これ以上追及しても稼げないとして、次の反論を探す |

- 点数は各モデルが自分で付け、どの主張を捨てるか、どの反論を追及するかを決める作戦に使う。投了・引き分けの判定にも、勝敗の判定(`judges` / `verdict`)にも使わない。
- 主張の点数を「審判が付けるであろう点数の見込み」とするのは、見込みを正確に付けることが評価を上げることにつながるようにするため。審判が低く見る主張を訴え続けると、`response` の評価が下がる(→「採点の基準」)。
- 一覧は毎ターン動的に編集する。主張・反論の追加、点数の更新、主張を捨てることができる。IDはターンをまたいで同じ項目を指す。
- 主張は、自分の立場が良い理由で、相手の主張がなくても成り立つものとする。相手の主張の弱さを突く論点は、主張ではなく反論一覧に書かせる。自分の立場に反する内容は書かせない。
- 主張は、自分の最初の発言のあとも、作戦メモの更新として足せる。ただし、足すように促す指示はしない(→ `decisions.md`)。足した主張も守る対象になり、投了の判定に含まれる。
- 一度作った項目は一覧から消さない。主張は「捨てる」、反論は点数を下げて「断念」にする。
- 主張の撤回は、発言で述べてよい(→ `prompts.md`「発言のルール」)。撤回するかどうかは討論者の判断に任せ、評価の基準(`logic`)で、崩された主張は撤回を明言するよう促す。論破された主張は撤回するのが議論の作法で、相手もその主張を崩せたと分かる。
- モデルには、新しい項目と変えた項目だけを出力させる。エンジンが前回の作戦メモと合わせて全項目の一覧にし、それを保存して次のターンに渡す。同じIDの項目は前回の位置で置き換え、新しい項目は末尾に足し、出力にない項目は前回の内容のまま引き継ぐ。項目が増えても出力が膨らまないようにするため。削除はできない(出力にない項目は引き継がれる)。
- 前回の作戦メモにあるIDの項目は、変える欄だけを書けばよい。書かれていない欄(内容・対象・点数・状態)は、前回の値で補う。新しいIDの項目は、すべての欄を必須とする。
- 立場(`positions`)は変えない。個々の主張は、守りきれなければ捨ててよい。
- 同じ反論を追及する回数に上限は設けない。モデルには毎ターン「このターンを含めた残りの発言回数」を伝え、残りの回数の中でどの反論に力を使うかを判断させる。
- 作戦メモは本人にだけ渡す。相手のプロンプトにも審判のプロンプトにも入れない。
- 作戦メモは、議論の終了後に開示する。議論中は表示しない。画面は後で作る(→ `04-app`)。今はMessagesに保存するだけとする。

### 投了

先攻・後攻の発言を生成するたびに、エンジン(Lambda)がその発言者の作戦メモを確かめ、守っている主張(`defending`)が1件もなければ、その発言者は投了する(負けを認める)。

- 判定はモデルではなくエンジンが機械的に行う(主張を捨てるかはモデルが決め、投了かどうかはエンジンが決める)。
- 反論(攻め手)の状態は投了の判定に使わない。攻め手が尽きても、守っている主張が残っていれば負けではない。
- 投了した場合、そのターンの発言は「負けを認める発言」に差し替える。作戦メモは差し替えずに保存する。
- 投了の発言を保存したところで、議論を終える。
- 結果として、終了理由(`endReason`)と投了した側(`concededBy`)をDebatesに保存する(→ `02-data-model`)。

### 引き分け

ターン4以降、先攻・後攻の発言を生成するたびに(投了しなかった場合)、エンジンが次を確かめる。

- 今回の発言者の作戦メモに、追及中(`pursuing`)の反論が1件もない。
- 相手の最新の作戦メモにも、追及中の反論が1件もない。

両方を満たせば、両者の攻め手が尽きたとして引き分けにする。

- ターン3までは判定しない(立論では両者の反論一覧が空で、ターン3の時点では後攻がまだ攻めていないため)。
- 引き分けになったターンの発言は差し替えない。
- 引き分けになったターンの発言を保存したところで、議論を終える。
- 終了理由(`endReason`)は `exhausted` とする。

### 根拠のルール

- 固有の事実(調査名、統計の数字、人名、企業名など)は、資料一覧の番号を付けて引用するときだけ使ってよい(例:「[3]によれば…」)。資料にない固有の事実は出さない。
- 資料のない根拠は、論理、一般的な知識、仮の例(仮の例であると明示する)で示す。
- 相手の根拠が示されていない、不確かである、または引用が資料の内容と合っていなければ、それを指摘してよい(反論一覧に加えられる)。

### Web検索と資料一覧

先攻・後攻は、自分の番に必要ならWebを検索できる。検索結果は、議論全体で共有する資料一覧に通し番号で登録する。

| 項目 | 内容 | 状態 |
|---|---|---|
| 検索の方式 | 討論者に検索の道具(Converseのツール `search`)を渡す。討論者が検索を依頼すると、Lambdaが検索用のモデルにWeb検索させ、結果を資料一覧に登録して討論者に返す。討論者は結果を読んでから作戦メモと発言を出力する | 確定 |
| 検索用のモデル | Amazon Nova 2 Lite のWeb検索(Web Grounding)。`us-east-1` の `us.amazon.nova-2-lite-v1:0`(東京リージョンでは使えないため、検索だけ米国で処理する)。EngineStackでLambdaの環境変数として設定する | 確定 |
| 1ターンの検索回数 | 3回まで。超えた依頼には、上限に達したことを返す(検証しながら見直す) | 確定 |
| 資料1件 | 検索1回で1件。番号、検索したターンと側、検索語、事実の要約(600字まで。超えたら切り詰める)、出典のURL | 確定 |
| 通し番号 | 議論全体で1から振る。どちらが検索した資料も同じ一覧に入る | 確定 |
| 共有 | 資料一覧は、先攻・後攻の両者(攻防の毎ターン)と審判に渡す。相手が検索した資料も読める。立論のターンには渡さない(相手の資料を見ずに立論させるため。→「ターンと段階・話者の対応」) | 確定 |
| 保存 | 資料は、検索した発言と一緒にMessagesへ保存する(→ `02-data-model`)。資料一覧は、全発言の資料をターン順に並べたもの | 確定 |
| 引用の記録 | エンジンは発言から引用された番号(`[n]`)を取り出して保存する。資料一覧にない番号は、記録するだけにする(生成し直さない) | 確定 |

- 検索結果は、検索用のモデルがまとめた要約。元のページの本文ではないため、内容がゆがむおそれがある。出典のURLを残し、人が後から確かめられるようにする。
- 投了の発言を生成する呼び出しでは、検索の道具を渡さない。

## Step Functionsの状態遷移

1. 初期化: Step FunctionsからDynamoDBを直接更新し、Debatesの `status` を `running` にする。ターン番号を1にする。議論IDがDebatesにない場合は失敗とする。
2. 発言生成: 発言生成Lambdaを呼ぶ。
3. 終了判定: Lambdaの出力の `finished` が `false` なら、ターン番号を1増やして2へ戻る。`true`(議論を終えた)なら4へ進む。
4. 判定: 終了理由が `maxTurns` なら、判定Lambdaを呼ぶ(→「優劣判定」)。投了・引き分けなら呼ばない。
5. 完了処理: Step FunctionsからDynamoDBを直接更新し、`status` を `done` にする。あわせて、終了理由(`endReason`)をLambdaの出力から保存する。投了で終わった場合は、投了した側(`concededBy`)も保存する。
6. 失敗時: どの状態で失敗しても、`status` を `failed` にして実行を失敗で終える。

### 発言生成Lambdaの入出力

| 項目 | 内容 |
|---|---|
| 入力 | `{ "debateId": "…", "turn": 1 }` |
| 出力 | `{ "debateId": "…", "turn": 1, "finished": false, "endReason": null, "concededBy": null }` |

- `finished`: このターンの発言で議論を終えたら `true`(ターンNの発言、投了の発言、引き分けになったターンの発言)。
- `endReason`: `finished` が `true` のとき、`maxTurns`(最大ターン数に達した)、`conceded`(投了)、`exhausted`(引き分け)のいずれか。それ以外は `null`。
- `concededBy`: 投了で終わったとき、投了した側(`pro` / `con`)。それ以外は `null`。
- 話者・段階・終了はLambdaが決める。Lambdaは議論IDでDebatesとMessagesを読み、ターン番号と `maxTurns`、そのターンの発言が投了・引き分けになったかから判断する。
- N を超えるターン、または投了・引き分けの発言より後のターンで呼ばれた場合は、エラーにする(再試行しない。Step Functionsは終えた議論の次のターンを呼ばないため、起きるのは設定や実装の誤りのとき)。
- 再試行の対象になるエラーは、エラー名 `TransientError` で返す。
- 先攻・後攻の出力が決められた形式(→ `prompts.md`)になっていない場合は、エラー名 `OutputFormatError` で返し、再試行の対象にする(再試行すると発言を生成し直す)。
- モデルの応答が最大トークン数で切れた場合(Converse API の `stopReason` が `max_tokens`)も、`OutputFormatError` で返す。途中で切れた発言を保存しないため。対象は、先攻・後攻・投了の発言と、審判の採点。検索用のモデルの要約は対象にしない(長すぎる要約は切り詰めて使うため)。
- Bedrockを呼ぶたびに、モデルID、`stopReason`、出力のトークン数をログに残す。上限で切れることがどれくらい起きるか、何が出力を膨らませているかを確かめるため。
- 先攻・後攻の出力は、作戦メモ(`<notes>`)と発言(`<speech>`)の中身の字数もログに残す。最大トークン数で切れた出力も、切れた時点までの字数を残す。どの部分が出力を膨らませているかを分けて確かめるため。

### 実行方式と失敗時の扱い

| 項目 | 内容 | 状態 |
|---|---|---|
| ワークフローの種別 | Standard | 確定 |
| 発言生成の呼び出し | Step FunctionsからLambdaを呼び、LambdaがBedrock(Converse API)を呼ぶ | 確定 |
| 発言生成Lambdaの処理 | Debatesから設定、Messagesから履歴を読み、ターン番号から話者と段階を決め、プロンプトを組み立ててBedrockを呼ぶ。先攻・後攻の場合は検索の依頼に応え(→「Web検索と資料一覧」)、出力から作戦メモと発言を取り出し、引用された資料の番号を記録し、投了と引き分けを判定する(投了ならBedrockをもう1回呼んで負けを認める発言を生成する)。Messagesに保存する | 確定 |
| 再試行 | Bedrockのスロットリング・一時的な障害、Lambdaの一時的なエラー、出力の形式の誤りのみ。最大3回、間隔2秒から倍々に延ばす | 確定 |
| 再試行しないエラー | 上記以外(設定の誤り、モデルIDの誤りなど)。`status` を `failed` にして終了する | 確定 |
| Lambdaのタイムアウト | 発言生成は5分(検索を最大3回行うため)、判定は5分(考える過程を長く出すモデルがあるため) | 確定 |
| 二重保存の防止 | Messagesへの保存は、同じ `debateId` と `turn` の発言がない場合のみ書く条件付き書き込みにする。既にあれば保存済みとして次へ進む | 確定 |

## Bedrockの呼び出し設定

| 項目 | 内容 | 状態 |
|---|---|---|
| 最大トークン数 | 1回の呼び出しあたり8,000。途中で切れないための安全幅とし、実際の長さはプロンプトの字数の指示で抑える | 確定 |
| temperature | 0.7 | 確定 |
| 発言の長さの目安 | 立論・攻防は400字程度、投了は300字程度。プロンプトで指示する。立論・攻防の実際の発言は指示より長く(約600字)、当面はこの長さを許容する(→ `decisions.md`) | 確定 |

- 全役割で共通の値とする。
- 検索用のモデルの呼び出しは、最大トークン数 1,500、temperature 0.3(事実の要約のため低めにする)。

## 動作確認用のモデルの組み合わせ

モデルはコードに固定せず、議論ごとの `participants` で指定する。開発初期の動作確認では次の組み合わせを使う(`ap-northeast-1`)。

| 役割 | モデル | モデルID |
|---|---|---|
| 先攻 | Claude Haiku 4.5 | `jp.anthropic.claude-haiku-4-5-20251001-v1:0` |
| 後攻 | Claude Haiku 4.5 | `jp.anthropic.claude-haiku-4-5-20251001-v1:0` |
| 審判1(`judges`) | Claude Opus 4.6(観点 `logic`) | `global.anthropic.claude-opus-4-6-v1` |
| 審判2 | Claude Opus 4.6(観点 `evidence`) | `global.anthropic.claude-opus-4-6-v1` |
| 審判3 | Claude Opus 4.6(観点 `exchange`) | `global.anthropic.claude-opus-4-6-v1` |

- 先攻と後攻は同じモデルにする。作戦メモ・追及・投了の仕組みを、モデルの性能差に左右されずに確かめるため。
- 画面(HTTP API)から作る議論では、先攻と後攻のモデルと、審判のモデル(3人とも同じモデル。観点はそのまま)を選べる(→ `04-app`「選べるモデル」)。上の組み合わせは、その既定値として使う。
- 先攻・後攻は `jp.` の推論プロファイルで国内処理にする。
- 安価で応答の速いモデルを選ぶ(動作確認で繰り返し実行するため)。
- 審判は Claude Opus 4.6 を3人とし、観点(論理、根拠、反論・応答)を分ける。審判は議論を読み比べる役のため、呼べるモデルの中で議論を読む力が十分なものに任せる。1人だと、判定が1人の見方だけになり、公正な結果に見えにくい。
- 審判の Opus 4.6 は `global.` の推論プロファイルでしか呼べず、日本の外で処理されることがある。
- 3人とも同じモデルのため、Claude の討論者をひいきする傾向があれば、3人そろって同じ側に寄る。Claude 同士でない議論の判定でも確かめる。
- 動作確認用CLIの既定のターン数は10(各側5回。AIの議論を見て楽しみたい人が、最後まで読める長さにするため)。仕組みの検証(主張の扱い、作戦メモの膨らみなど、長い議論で出やすい問題を見るとき)では、30などを指定して動かす。

## 優劣判定

| 項目 | 内容 | 状態 |
|---|---|---|
| 判定する議論 | 最大ターン数で終わった議論のみ。投了で終わった場合は投了した側の負け、引き分けで終わった場合は引き分けとし、審判は呼ばない | 確定 |
| 配置 | Step Functionsで、議論を終えた後に「判定」状態を置く。判定中も `status` は `running` のままとし、判定を終えてから `done` にする | 確定 |
| 審判 | `judges` で指定する。先攻・後攻と同じモデルでもよい | 確定 |
| 観点 | 審判ごとに `judges[].viewpoint` で指定できる(省略可)。`logic`(論理の審判: 主張と理由の筋道に飛躍がないか、前の発言と矛盾していないか)、`evidence`(根拠の審判: 引用が資料の内容と合っているか、根拠の出どころが確かか)、`exchange`(反論・応答の審判: 反論が相手の主張を崩しているか、受けた反論に正面から答えているか)のいずれか。観点は、議論を読むときに特に注意するところとしてシステムプロンプトで伝える(→ `prompts.md`「審判」)。4つの基準は観点によらず同じ基準で採点させる。合計点は、観点の基準(`logic` は `logic`、`evidence` は `evidence`、`exchange` は `rebuttal` と `response`)の点を2倍にして足す。重みはエンジンが付け、審判には伝えない(重みを気にした採点にしないため)。理由は、観点から見た評価を中心に書かせる。同じモデルの審判を並べても、判定の見方が分かれるようにするため | 確定 |
| 人数 | `judges` の件数で決める。動作確認では3人にする(→「動作確認用のモデルの組み合わせ」) | 確定 |
| 入力 | 発言の全文、資料一覧、両者の最終の主張一覧と反論一覧(→「項目ごとの採点」)、議論の最後の発言がどれか(ターンと側)。話者は立場の名前(「週休3日制側」など)のラベルのみで、モデル名は伏せる。作戦メモの点数と状態は渡さない(自己採点に引きずられないため) | 確定 |
| 採点 | 先に両者の主張と反論ごとに点数を付け(→「項目ごとの採点」)、それを踏まえて、下の4つの基準を先攻・後攻それぞれ0〜10の整数で採点し、側ごとに理由を書く | 確定 |
| 見方 | 2つの立場のどちらがよく論じられたかを比べる。テーマについてどちらの立場が正しいかでは採点せず、どちらか一方の立場だけに立証の責任を負わせない | 確定 |
| 勝者 | 審判ごとに、4つの基準の合計点(観点がある審判は、観点の基準の点を2倍にした合計)が高い側を勝者とする(同点なら引き分け)。議論の勝者は、審判ごとの勝者の多数決で決める。過半数の審判が同じ勝者(先攻・後攻・引き分けのいずれか)を選ばなければ引き分け。合計と勝者はエンジンが計算する(モデルには点数と理由だけを出させる)。項目ごとの点数は合計に入れない | 確定 |
| 出力 | JSON(→ `prompts.md`「審判」) | 確定 |
| 保存 | Debatesの `verdict` に、審判ごとの結果の配列と、多数決の勝者を保存する(→ `02-data-model`) | 確定 |
| 偏り対策 | 観点の異なる審判を3人にし、多数決で決める。審判の入力ではモデル名を伏せる。発言順の入れ替えなどは、傾向を見て検討する | 確定 |
| 完了通知への掲載 | 判定結果を完了通知に載せる(→ `04-app`。画面を作るときに詳細を決める) | 推奨 |

### 項目ごとの採点

| 項目 | 内容 | 状態 |
|---|---|---|
| 対象 | 両者の最終の作戦メモにある、すべての主張(討論者が捨てた主張も含む)と反論(断念した反論も含む)。最終の作戦メモは、その側の最後の発言のもの。ただし、議論の最後の発言で初めて足した反論(答える機会のない反論)は対象にしない | 確定 |
| 主張の点数 | 0〜10の整数。その主張が、議論の流れの中で相手の反論を受けてもどれだけ持ちこたえたか。相手の反論に根拠付きで答えられていれば高く、答えられていない反論(答える機会のない反論は除く)が残っていれば低い | 確定 |
| 反論の点数 | 0〜10の整数。その反論が、議論の流れの中で相手の主張をどれだけ崩したか。相手が根拠付きで答えられなかった・はぐらかしたら高く、相手が根拠付きで答えていれば低い | 確定 |
| 区切り | 主張は8点以上を持ちこたえた主張、3点以下を崩された主張とみなす。反論は8点以上を効いた反論、3点以下を効かなかった反論とみなす(作戦メモの反論の点数の区切りに合わせる) | 確定 |
| 発言にない項目 | 作戦メモにあっても、発言で一度も述べていない項目は0点とする | 確定 |
| 使い道 | 主張の点数は `logic`(崩された主張の扱い)と `response`、反論の点数は `rebuttal` の採点で踏まえる(→「採点の基準」)。`logic` は、主張と反論を通した自分の発言の一貫性で採点する。合計点には入れない。議論の後に、討論者の点数と比べて分析する(→ `analysis.md`) | 確定 |
| 理由 | 項目ごとの理由は書かせない(出力を短く保つため) | 確定 |

- 審判には、主張はIDと内容、反論はIDと対象と内容だけを渡す。討論者が付けた点数と状態(守る・捨てる、獲得・追及中・断念)は渡さない。
- 議論の最後の発言で初めて足した反論は、その側の最後から2番目の作戦メモにないIDの反論とする。

### 採点の基準

基準の文の前に、基準で使う言葉の意味(用語)を置く。討論者と審判の両方が読むため、どちらの側からでもない書き方にする。審判は作戦メモの説明を受け取らないので、基準の言葉の意味はここで伝える。

| 用語 | 意味 |
|---|---|
| 主張 | 各側が、自分の立場が良い理由として立てる論点。相手の主張がなくても成り立つもの |
| 反論 | 相手の主張の弱さを突く指摘 |
| 追及 | 同じ反論を、ターンをまたいで続けて突くこと |
| 受けた反論 | 自分の主張に向けられた、相手の反論(相手の追及を含む) |
| 崩された主張 | 受けた反論に、根拠付きで答えられていない主張。審判が3点以下と見なす主張 |
| 持ちこたえた主張 | 受けた反論に、根拠付きで答えられている主張。審判が8点以上と見なす主張 |
| 資料 | 検索で集め、資料一覧に番号付きで載っている事実の要約 |
| 引用 | 発言の中で、資料の番号([3] など)を付けて資料の内容を使うこと |
| 答える機会のない反論 | 議論の最後の発言で出た反論。相手にはもう発言の番がないため、答えられない |


| キー | 基準 | 評価が高い | 評価が高くない |
|---|---|---|---|
| `logic` | 論理の一貫性 | 主張と理由のつながりが明確で、自分の前の発言と矛盾しない。審判が3点以下と見なす主張(崩された主張)は、撤回を発言で明言し、残る主張で論じる | 推論に飛躍がある。自分の前の発言と矛盾する。審判が3点以下と見なす主張を、撤回を明言しないまま放置する |
| `evidence` | 根拠の確かさ | 固有の事実に資料の番号を付けて引用し、引用が資料の内容と合っている。根拠の主軸を公的機関・研究機関・報道機関の資料で裏付ける。資料のない根拠は論理・一般的な知識・仮の例で示す | 個人のブログや個人の記事(出典のURLで判断する)を根拠の主軸にする。資料と食い違う引用をする。資料のない固有の事実を断定する |
| `rebuttal` | 反論の的確さ | 相手の主張や引用を具体的に崩す。自分の主張の良さを示したうえで、その対比で相手の主張の弱さを示す。同じ反論の追及を続けるときは、新しい根拠か新しい角度を加える。相手の主張の中から、崩す効果が最も大きいものを選んで、反論を深く追及する | 新しい根拠も新しい角度もないまま、既存の根拠で同じ反論を言い直す。相手の発言とかみ合わない。相手の主張の多くに毎回少しずつ反論し、1つずつの掘り下げが浅い |
| `response` | 受けた反論への応答 | 受けた反論のうち、自分の主張にとって影響の大きいものに正面から答える。審判が8点以上と見なす主張(相手の反論に持ちこたえた主張)を軸に論じる | はぐらかす。前と同じ説明を繰り返す。審判が3点以下と見なす主張(根拠付きの反論に答えられていない主張)を、補強せずに訴え続ける。影響の大きい受けた反論に答えず、小さな反論への答えだけで済ませる |

- 統計やデータを示していないこと自体は、評価を下げない。
- 1回の発言で扱う主張や反論が少ないこと自体は、評価を下げない。論点を選んで深く論じることを促すため(論点を毎回すべて並べると発言が長くなり、1つずつが浅くなる)。
- 答える機会のない反論に答えていないことは、`response` の評価を下げない。答える機会のない反論だけを理由に、相手の主張を崩された主張と見なさない。答える機会のない反論は、`rebuttal` の評価に入れない。後攻の最後の発言には先攻が答えられないため(最後に新しい攻撃を出しても点にならないようにする)。最後の発言での受けた反論への答え(守り)は、ほかの発言と同じく評価する。
- この基準は、審判だけでなく先攻・後攻にも同じ文で伝える。討論者には、作戦メモの点数もこの基準を踏まえて付けさせる(→ `prompts.md`)。
- 同じ反論の追及を続けること自体は評価を下げない(追及の回数に上限は設けない)。評価を下げるのは、新しい根拠も新しい角度もない言い直しだけ。

### 判定Lambda

| 項目 | 内容 |
|---|---|
| 入力 | `{ "debateId": "…" }` |
| 処理 | Debatesから設定、Messagesから全発言と両者の最終の作戦メモを読み、`judges` の審判ごとにBedrockを呼んで採点させる(審判は同時に呼ぶ)。審判ごとの合計と勝者、多数決の勝者を計算し、項目ごとの点数とあわせてDebatesの `verdict` に保存する |
| `judges` がない場合 | 何もしない(`verdict` は作らない) |
| 二重保存の防止 | `verdict` が既にあれば何もしない。保存は `verdict` がない場合のみの条件付き書き込みにする |
| 再試行 | 発言生成Lambdaと同じ(一時的な障害と `OutputFormatError`。応答が最大トークン数で切れた場合を含む)。再試行では、すべての審判を呼び直す |
| 呼び出し設定 | 最大トークン数 8,000(考える過程を長く出すモデルがあるため)、temperature 0.2(採点のぶれを抑える) |
| タイムアウト | 5分 |
| 資料一覧 | 全発言の資料をターン順に並べて渡す |

- 審判の結果は、多数決でまとめる(→「優劣判定」の「勝者」)。平均点にしないのは、極端な点を付けた1人の審判に全体が引っ張られないようにするため。
